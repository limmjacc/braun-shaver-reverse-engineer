And so at this point, the approach I wanted to take was clear: Lets use voltage based fault-injection to hack into the device. Now you might be wondering: What is fault-injection, or, as it’s more commonly called, glitching? Well,simplified, if you take the power-supply to for example a micro-controller, and you interrupt it for a verrrrry short amount of time, you can manage to change the behavior of the chip. And so for example you can corrupt memory reads, and even skip instructions. NOw if we imagine the boot of chip, at some point in time there might be a check that is similar to this: The chip checks whether debugging is disabled. And if it is, it will skip enabling the debugging hardware. However if we manage to glitch during the exact time of the check, we might be able to trick the chip into enabling the debugging hardware. And that’s exactly what I did on the AirTag. A Naturally, this is not super trivial, but it’s also not very hard! The first thing we have to figure out is: What do we want to glitch? If you look at a microcontroller, you will often see that it has a single power supply of lets say 1.8V. However in the chip, often other voltages are generated using regulators. And so for example the CPU core might run on a different voltage than the bluetooth peripheral and so on.Now when we glitch, we really want to try to only glitch for example the CPU core, which isn’t really possible when we would try to glitch on the 1.8V supply. However, regulators tend to be noisy, and to compensate that, there are often external decoupling capacitors external to the chip. And these capacitors, give us direct access to the voltage of for example the CPU core! And so if we attach a switch to ground to that capacitor, and we press down the switch, we create a short circuit to ground that will interrupt the power to the CPU core. And if we open the switch again, power will be back. Now obviously with a physical switch, you won’t be able to do this super precisely, and so instead of a switch, we can use an n-channel mosfet, and instead of triggering it with our fingers, we can use a device. Now normally you’d use an FPGA or something else with very precise timings, but I thought it be fun to try to glitch the AirTag,.. With a 4 dollar raspberry pi pico. And so if the Pico will enable the GPIO, the power to the CPU core will get interrupted. And if the GPIO goes down again, the power will be restored. Now how does this work on the real device? Luckily for us, the capacitor for decoupling the CPU core voltage, is easily accessible on the under-side of the device. you don’t even have to remove the PCB from the Tag, you just need to remove the backside. And even better, there’s a nice testpad connected to it, which makes soldering much much easier. Now a fair warning: I was impatient when I soldered this on my AirTag, and I immediately ripped off that testpad and had to solder directly onto the pads of the capacitors instead. So be careful if you try this at home! Now basically, I connected that CPU core testpad to my raspberry pi pico using an n-channel mosfet. Then, for the pico to detect when the nRF is turned on, I also connected the power-supply of the nRF to the Pico - I had use a level-shifter here, as the Pico runs at 3.3V and the nRF itself is running at 1.8. I also connected the battery contacts of the AirTag directly to my raspberry pi, so that I could control when the AirTag is powered on. All that’s left to do now is to connect an SWD programmer to the programming pins that were found by Colin O’Flynn, and so after each glitch, we will simply try to connect to the chip using SWD, and if it succeeds, we were successful! And the nice thing is: We can try this a ton of times! In fact, we can restart the Tag, glitch it, and then try to connect multiple times per second. And so we don’t have to be super precise, we can basically brute-force it! For the timing on where to glitch, I again looked at limited result’s blogpost, and saw that he glitches roughly where the CPU core voltage slightly dropped. And so using the oscilloscope I found that point in time, and set it up. For the pulse-width I used the pulse-width I used back in 2019, as I very extensively experimented with different ones back then.
